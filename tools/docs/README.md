# Documentation website

The public site presents **Wistia PHP 2.0.0**, with usage guides and PHP API reference
generated by phpDocumentor. Reader-facing copy is prepared for the release; that does not
create a package tag or publish a library release. Publisher credit appears only in the
footer; required PHP namespaces, package names and source URLs remain unchanged.

## Build and check locally

Requires PHP 8.4+ with DOM/XML, mbstring and intl. The documentation build does not load
Composer's application autoloader, `.env`, Wistia credentials or live tests.

```sh
php tools/docs/install.php
php tools/docs/build.php
php tools/docs/check.php
php tools/docs/check-examples.php
php tools/docs/check-repository-links.php
php -S 127.0.0.1:8080 -t build/site
```

The installer downloads **phpDocumentor 3.10.0** from its official GitHub release and
verifies its SHA-256 digest before use. The PHAR stays in ignored `.tools/`; it is not a
library dependency. Change both the version and checksum when upgrading the generator,
and renew the build, link and rendered-page checks. The checksum comes from the
[release asset metadata](https://api.github.com/repos/phpDocumentor/phpDocumentor/releases/tags/v3.10.0).

`phpdoc.dist.xml` selects public PHP symbols from `src/`. Reader-facing prose lives in
`docs/site/`: a first-call tutorial, task-based how-to guides, lookup references, concept
explanations and framework integration guides. Write for PHP developers who know Composer
and are new to this client. Keep prerequisites, remote effects and expected results explicit.

`navigation.php` owns the reading order and the exact Markdown publish allowlist. Add every
new public page there; the checker rejects unlisted source pages. `build.php` stages only
that allowlist. Links to library source symbols become generated PHP-reference links;
example/source-record links remain on GitHub. Duplicate top-level usage guides have been removed; README points readers to the website.
Keep `docs/site/` as build source, `docs/reference/` and `docs/rewrite/` as internal
contract/evidence records, and example READMEs as exact setup recipes. Historical helper
verification statements are retained in `docs/rewrite/helper-evidence.md`. Keep milestone
IDs, source hashes and delivery-test reports in internal records, not the public guides.

`decorate.php` adds navigation, the 2.0.0 version label, a neutral product favicon and the
footer with publisher credit and “Hosted at Spacefast”. It also works around phpDocumentor 3.10's Markdown
fragment-link resolution. The root page is the documentation overview; `api.html` retains
the generated API index. The sidebar uses one consistent list hierarchy, groups tasks and
marks the current page. `legacy.php` maps the first site's old public URLs to rewritten
pages with canonical links and static refreshes, without copying historical prose.
The historical installation fragment is inserted during decoration because phpDocumentor
drops raw Markdown anchors; the generated-page checker requires both old and current IDs.

`check.php` checks rendered HTML links/anchors, page/navigation parity, sidebar structure,
branding and allowed publish-file types. `check-examples.php` parses the public PHP
fragments, checks imported symbols, known service methods and constructor argument names,
and executes the actual first-call tutorial and migration read through injected synthetic transports.
It uses a source-only autoloader, no Composer setup hooks or real environment credentials.
Other snippets are statically checked, not executed against Wistia. Neither check contacts
external documentation. The service directory is checked against every implemented service.
`check-repository-links.php` separately checks local Markdown targets and heading anchors
in the README, source guides, example setup instructions and internal records, without
requesting external URLs. This protects against stale links when retired guides are removed.

For layout changes, inspect a guide and an API-reference page at 390px, 1280px and
1920px widths. With an installed `agent-browser` and a page open, run:

```sh
agent-browser eval --stdin < tools/docs/check-layout.js
```

This checks that the header and footer match the centered body container, that the
footer follows both documentation columns, that the page has no horizontal overflow,
and that sidebar link labels retain at least 10px of padding inside their left borders.
Check the inset in normal, hover and keyboard-focus states so upstream template rules
cannot collapse it. In particular, wide-screen checks catch float layout
problems that can remain hidden at narrower desktop sizes.

The default phpDocumentor template loads syntax-highlighting, icons and API search
libraries from public CDNs. Documentation text and navigation remain readable without
those enhancements; API search and highlighting depend on those services.

## Publish

`.github/workflows/docs.yml` builds and checks pull requests without deployment secrets.
On `main`, a successful build uploads its generated site artifact and the deploy job
publishes **only `build/site/`** to the Space ID in `.spacefast/space.json`. A failed build
cannot start deployment. Production publishes are serialized; superseded main revisions
are skipped before publishing. No branch-protection checks are made mandatory by this
workflow.

Deployment requires the repository secret **`SPACEFAST_TOKEN`**. Use a key restricted to
the linked Space and the read/publish/build permissions required by Spacefast. Provisioning
or rotating a key and storing it in GitHub require maintainer approval. Never commit or
print keys, Spacefast credential files, `.env`, or publish a repository-root archive.
Local `.spacefast/state.json`, build output and PHAR/cache files are ignored.

With an authorized CLI session and an existing link, a manual update is:

```sh
php tools/docs/build.php
php tools/docs/check.php
php tools/docs/check-examples.php
php tools/docs/check-repository-links.php
sf publish build/site --prebuilt --space "$(php -r 'echo json_decode(file_get_contents(".spacefast/space.json"), true, flags: JSON_THROW_ON_ERROR)["space"];')" --wait
```

Inspect the receipt for activation and verify the public URL after publishing. On an
uncertain write, follow Spacefast's status/idempotency instructions instead of creating
another Space. The committed link identifies the deployment target; it contains no key.

The initial hosting destination is the maintainer's Spacefast account, using a managed
hostname. Spacefast supports transfer to another team with acceptance by its member.
Revisit publishing credentials and account/plan eligibility when ownership changes.
Custom domains and 1.x documentation are outside the initial scope. Hosting never grants
permission for paid upgrades, purchases or changes to other Spaces.

## Branding sources

- White Automattic wordmark: `Automattic-logo-white.svg` in the official
  [Automattic brand kit](https://automattic.com/wp-content/uploads/2026/10/automattic-brand-kit.zip),
  linked from [Brand Materials](https://automattic.com/press/brand-materials/).
- Favicon: the official 32px [Automattic site icon](https://automattic.com/wp-content/uploads/2026/10/a8c-favicon-1.png?w=32), linked by automattic.com.
- Colors: Automattic's `a-8-c` palette exposed by [automattic.com](https://automattic.com/):
  dark blue `#00425B`, blue `#0277A8`, pale blue `#EBF4FA`, and gray `#C3C4C7`.

These earlier brand assets remain as source provenance but the wordmark and publisher
favicon are no longer published. `wistia-php.svg` is the product's neutral W monogram;
the existing blue palette is retained. Publisher attribution is confined to the footer,
not page titles, header imagery or introductory prose. Technical namespace/package
identifiers are not branding and must not be rewritten. Hosting ownership is not authorship.
