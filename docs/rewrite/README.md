This is a planning inventory, not a list of installed endpoint coverage. ## Status and sources

[operations.json](operations.json) is the authoritative operation inventory and per-operation contract mapping. It pins the exact #8/#9 body SHA-256 digests and `updated_at` values, the first-party catalog digest, and each fetched reference page's digest. Checked **2026-10-15**: **167 catalog operations = 139 Data + 10 Stats + 17 Analytics + 1 Upload; 161 included and 6 excluded**. No count drift was observed. The root Upload entry covers file upload and URL import; the six separately enumerated upload workflows are **not** six additional catalog operations.

The inventory was reconstructed from the [official catalog](https://docs.wistia.com/llms.txt) and all 167 operation pages, plus nine linked first-party guides. The earlier analysis mentioned by #8 was not available as a separate authoritative inventory; its approved decisions were reused, but its unprovided analysis was not fabricated. Source digests pin fetched Markdown bytes, not an independently verified server implementation. Examples and generated SDK samples were not copied as fixtures. Relevant input/output schema descriptions and constraints were retained; duplicate wire schemas share a source-named definition within the same inventory.

**Delivered by P01:** inventory, this reference, the [ADR](../adr/0001-typed-api-contracts.md), and an offline inventory consistency checker; P01 delivered no runtime or Composer changes. **Later implementation:** P02 provides the shared foundation and offline harness; P04 implements the [OAuth helpers](../oauth.md) listed below. **Planned:** catalog method/DTO/docs/test targets and other helpers in this checkout. **Unverified:** live behavior and the unresolved source-response contracts below. PHP 8.4/newer-runtime offline execution is recorded in the root README, not claimed as P01 evidence. Passing inventory checks is not WIS implementation acceptance.

## Operation contracts

Each catalog record has a stable `id` equal to its reference slug, a family/group, exact source URL/digest, HTTP method/base/path, inclusion or exclusion, experimental status, source-described restrictions and downstream owning issue. Included records map to explicit public **method/request/result targets**, documentation and offline contract-test targets. These paths are work destinations, not links to files claimed to exist.

Read a record as follows:

- `http`: `base_uri` + `path` is the request URL. Replace each named path component with its encoded identifier, not a pre-encoded whole path. The checker matches required path inputs to placeholders.
- `planned.method`: resource service and explicit method, not magic dispatch. `request_type` and `result_type` are fully qualified targets under retained `Automattic\Wistia`. Method signatures are planned as `(NamedRequest $request): NamedResult`, including operations with no variable inputs. Service access/configuration construction belongs to #10, not an existing API asserted here.
- `request.parameters`: input location, exact wire `name`, PHP property mapping, required flag, schema type/enum/format/constraints, and parameter-specific encoding (`style`/`explode` when documented). Omitted `required` means optional. `php_property` preserves source spelling except removing a terminal `[]`; the array's wire name remains unchanged. Version headers are represented by `http.api_version`, not consumer-editable request properties.
- `request.narrative_derived`: additional planned typed inputs explicitly documented in prose but absent from generated parameters. Show Captions plans `ShowCaptionsRequest::format` with the string-backed `Request\Data\CaptionFormat` enum (`json` default, `srt`, `vtt`, `txt`). Append `.srt`/`.vtt`/`.txt` to the encoded language-code path component before the query; JSON uses the unextended path. Do not emit a `format` query parameter or format-selecting Accept header: the [source narrative](https://docs.wistia.com/reference/get_medias-mediahashedid-captions-languagecode.md) documents extensions, avoiding guessed Accept MIME values. `ShowCaptionsResult` preserves the selected format: JSON maps to the structured caption record, SRT/TXT to the documented `text/plain` string schema, VTT to the `text/vtt` string schema. #16's existing `tests/Contract/Data/ShowCaptionsTest.php` target must assert default/explicit JSON, all three extensions/text results, unchanged auth/version, no invented selector query/header, and JSON-only `include` versus TXT-only `include_speakers`. These are planned assertions, not executed endpoint tests; generated parameters/content/schemas remain unchanged.
- `request.content`: supported body content types, each referencing a `wire_schemas` definition. `body_required` is the source's requirement. Body properties use their exact documented names, including nested fields; source schemas define scalar types, lists/maps, required versus optional fields, nullable values and alternative structures. An omitted field is distinct from explicit `null` (especially partial customization updates). No global snake/camel-case converter may rewrite requests.
- `responses`: status-specific response descriptions, content types, optional headers and named wire schemas. Each schema reference resolves within `wire_schemas`. A result target represents the applicable success schema(s), including bare arrays, envelopes and text; it is not permission to assume every response is a Media object or every success is 200. Error responses feed the shared failure contract. Preserve documented mixed-case response fields such as `embedCode` and Stats `fileSize`; do not blindly normalize response keys either.
- JSON Schema types describe the **wire** contract, not already-generated PHP classes or proof that the server enforces every constraint. Downstream typed nested records/lists must preserve those shapes. Open-ended maps remain typed maps rather than magic service dispatch. Source discrepancies below override any claim of definitive generated-schema validation.
- `pagination`, `asynchronous`, `side_effect` and `safety_constraint`, where present, call out behavior that cannot be inferred from the HTTP verb or a single response schema.

For example, `get_medias` maps to `DataMediaService::listMedia`, `Request\Data\ListMediaRequest`, and `Result\Data\ListMediaResult`. Its request includes `folder_id`, repeated `hashed_ids[]`, and a nested cursor; its success body is an array, not an object envelope. `post_medias-import-url` instead sends JSON to `/modern/medias/import_url` and returns a background job. It is **not** the form-encoded Upload-host URL-import operation.

The `post_` catalog record is the shared wire contract for `UploadService::uploadFile` and `UploadService::importUrl`. Its `method`/`additional_method` entries alias the two named `upload_workflows`; those are single definitions, not duplicated methods. The retained source body schema includes deprecated `access_token`; `source_only_fields` marks it as provenance, **not** an approved public request property. The workflow fields govern the public Upload inputs and use only Bearer-header credentials. Other catalog operations and workflow definitions must have unique method identities (case insensitive, as in PHP).

## Hosts, authentication, encoding and results

| Contract | Planned request behavior | Planned result/failure behavior |
| --- | --- | --- |
| Data, Stats, Analytics | `https://api.wistia.com/modern`; `Authorization: Bearer …`; `X-Wistia-API-Version: 2026-09`. HTTP verb/path and JSON/multipart/query shapes come from each operation, not the older generic v1 guide. | Decode the operation's documented status/content/schema. Preserve relevant response headers. Invalid JSON/content/shape is a decoding failure, not a successful empty result. |
| Upload | Separate HTTPS Upload contract; no modern version header. Bearer header, never a credential-bearing query/body fallback. File is multipart; URL import is form-urlencoded. Exact per-workflow host/fields are in the inventory. | Root `/` has a documented 200 JSON media result, 400 JSON error and 401 HTML error. A successful upload may still be processing. Other workflow response gaps remain unresolved, not defaulted to that media schema. |
| OAuth | Authorize URL at `https://app.wistia.com/oauth/authorize`; exchanges at `https://api.wistia.com/oauth/token`; no modern version header. See helper targets below. | Typed token response and sanitized grant/authentication/decoding failures; consumer-owned persistence. |

Encoding must preserve exact wire names: `folder_id` in modern Data; `project_id` in Upload; `/stats/projects/{projectId}` still uses `projects`. Repeated bracketed list keys, deep-object `cursor[enabled]`, `cursor[before]`, `cursor[after]`, false/zero, omission and explicit null need distinct offline capture assertions. Do not encode `tags[]` as an unrelated comma-separated string, or double-encode signed URLs. For uploads, reject detectably invalid local files before network use; URL reachability, ownership, IAM access, remote processing and account entitlement remain remote validation.

Shared execution/encoding/decoding and injectable HTTP transport belong to #10. Preserve API/authentication/rate-limit/transport/decoding distinctions with useful sanitized exceptions; make supplied rate-limit information (including `Retry-After`) accessible. Never leak tokens, OAuth secrets/grants, signed source URLs or raw sensitive bodies through exception messages, logs or nested causes. No automatic retries and no credential-bearing redirects. A timeout/disconnect after a write may have reached Wistia: expose an **uncertain remote outcome**, not a false assurance that nothing changed or an implicit replay. This also matters for Show share link, a GET documented to create a share link on first access.

## Pagination and jobs

The approved strategies remain offset, Data cursor and Analytics cursor; do not merge them into one guessed universal cursor format.

- Offset uses the endpoint's page/per-page controls and termination semantics; preserve all supported filters and order. Stats Events and Visitors are offset contracts. Do not invent pagination for a non-paginated array response.
- Most Data cursor endpoints use nested `cursor` query parameters and record cursors. Cursor values are tied to the original sorting. Do not mix offset `page` with cursor mode; preserve filters/order and stop or report non-advancing traversal rather than loop forever.
- **Data webinar registrations is a source-documented variant:** scalar `cursor`, `sort_direction` 0/1, `registrations` plus `page_info` envelope. It is marked `data-cursor-page-info`, not sent through the nested record-cursor encoding. This is a variant within the approved Data-cursor responsibility, not an added API family or fourth promised adapter.
- Analytics conversions and webinar audience use scalar cursors and `data`/`page_info`; use the documented `has_next_page` and `end_cursor`, not array length or a guessed Data record cursor. Retain endpoint-specific date semantics: Analytics start is inclusive/end exclusive where specified, whereas Stats by-date ranges are inclusive.

Job-returning operations expose identifiers/status immediately. #11 owns `DataBackgroundJobStatusService::showBackgroundJobStatus` and finite optional polling. Queued/started/finished/failed states and per-action bulk partial failures must be observable; a finished job is not proof that all its actions succeeded. Bound local polling and stop on completion, reported failure or exhaustion. Stopping polling does not cancel a remote job. Order-status reads for existing audio-description orders remain included; they do not authorize placing an order.

`POST /bulk` is non-purchasing only: the inventory retains its documented action/job/resource enums and payload constraints. Exactly one of actions/job; limits include 1000 explicit actions, body under 2 MB and up to 5000 resolved job records. Typed discriminated payloads map to the corresponding included create/update/delete/move contract; this is not an arbitrary endpoint tunnel. #23 must test invalid combinations, oversized input and per-action failures without accidentally allowing excluded purchases/generation/trials.

## Upload workflows and unresolved contracts

Six explicit workflow definitions cover local file upload, URL import, thumbnail file upload, thumbnail URL import, S3 copy, and supplied-audio localization URL import. These retain their separate request/result targets. Supplied-audio localization import is included; generating/buying a localization via Data is excluded.

`contract_gaps` in the inventory is the authoritative named gap list. Under the maintainer-approved [P01/P16 boundary in #8](https://github.com/Automattic/wistia-php/issues/8), **#24 / P16 (uploads/imports)** must resolve the following contracts before implementing or accepting the affected workflows. P01 may complete by recording these gaps and their owner; all workflows and their final WIS obligations remain required. This is a planning responsibility adjustment, not an API exclusion or a new opaque-result commitment:

- The [thumbnail guide](https://docs.wistia.com/reference/update-thumbnails-via-upload-api.md), “The Request” and examples, gives POST `/thumbnail` and lowercase `url`, but its URL example omits POST and uses uppercase `URL`. No response status/body schema is given for either thumbnail workflow.
- The [S3-copy guide](https://docs.wistia.com/reference/upload-via-s3-copy.md), “Endpoint and Parameters,” gives fields, setup and form example but no response status/body schema. Do not silently reuse the root Upload response.
- The [Upload guide](https://docs.wistia.com/reference/getting-started-with-the-upload-api-1.md), “Importing Alternate Audio Localizations,” gives the supplied-audio fields and an explicit `upload-v2.wistia.com` example; general request prose says `upload.wistia.com`. It gives no localization-specific response schema. The inventory pins the example host as **source evidence, not a resolved host decision**; confirm host/result authority before implementing that workflow.

Result names for these four workflows are targets only; their result shapes remain partial. No schemas, fixtures, success codes, raw-body public result design or live results have been invented. Obtain authoritative documentation/clarification before #24 finalizes request fixtures/decoders. No Wistia account request is authorized to fill these gaps.

P02's configurable/shared transport must support separately documented hosts and content types, but does not need these missing response shapes to implement encoding, decoding primitives and errors. P03 Data job/pagination contracts, P04 OAuth and P05 webhook contracts do not depend on Upload's unresolved response shapes. Under the approved boundary, these four gaps do not block P01's inventory/planning acceptance or P02–P05 after P01's other obligations and required accepted integration are satisfied. They still block implementation and acceptance of the affected P16 workflows. Native dependency and integration gates remain unchanged.

## Source discrepancies and restrictions

- **Upload auth (resolved by #8):** the [older OAuth guide](https://docs.wistia.com/docs/authenticating-with-oauth2.md), “Perform an API request with OAuth credentials,” says Upload only accepts query tokens. The Upload-specific guide and [root Upload reference](https://docs.wistia.com/reference/post_.md) support/recommend Bearer headers and discourage legacy token parameters. Use Upload-specific Bearer authentication; do not copy the legacy client's `api_password` body field.
- **Upload error shapes:** the Upload guide's “Video Limit” example has a string `error`, while the root Upload schema describes an `error` object with `code`/`detail`; that reference's missing-credentials example instead flattens `code`/`detail`. The inventory preserves the schema as source evidence, not proof of one universal error envelope. #10/#24 must exercise these documented variants through sanitized status-based failures rather than assuming all errors match one object shape.
- **Media cursor sort (explicit #8 discrepancy):** [List Media](https://docs.wistia.com/reference/get_medias.md), `sort_by`, says cursor mode supports only `id` and `created`, but its enum lists `name`, `created`, `updated`, `position` and omits `id`. Preserve both pieces of source evidence. The narrative governs cursor restrictions; generated enum validation must not reject cursor `id` solely because of the enum or permit the offset-only options in cursor mode. No live resolution is claimed.
- **Modern versus generic v1 instructions:** the [migration guide](https://docs.wistia.com/docs/migration-from-v1-guide.md) describes `/modern` + version header; fetched operation schemas pin 2026-09. The older [request guide](https://docs.wistia.com/docs/making-api-requests.md) still illustrates v1/extensions and form bodies. Endpoint-specific modern schemas govern their JSON bodies; Upload and OAuth remain separate contracts. Do not append `.json` globally or rename Upload's `project_id` to `folder_id`.
- Experimental **Create Expiring Access Token** (`post_expiring-token`) is visibly marked experimental in the inventory and must remain so in its planned public reference. No other catalog operation was explicitly marked experimental by the checked sources. This is not a stability guarantee.
- Scope/permission requirements, delegated-contact authorization restrictions, plan/feature conditions, validation limits and source-described failure responses remain in each operation's `restrictions`, parameters, body schemas and response mappings. An absent plan condition is **unspecified**, not proof that a free account can call it. No paid-plan endpoint is live-verified.
- Official generic guides caution that APIs are primarily supported for videos in folders/projects, with limited formal support for audio/channel use. Endpoint-specific Channel/Episode and supplied-audio localization documentation is retained, not silently excluded by that older generic caution.
- Stats Events have a two-year retention limit; Analytics date windows/granularity, webinar state/entitlement failures, and source-specific time units remain per-operation contracts. Preserve these restrictions in downstream public docs instead of inferring interchangeability from similar endpoint names.

The six exclusions are enumerated only in the inventory: text translation, caption purchases, localization generation, audio-description orders, bulk purchases, account trials. Free allowances do not remove charge risk. Read-only plan/credit information and non-chargeable paid-plan operations remain included. Browser/player APIs, undocumented internal endpoints and consumer infrastructure remain outside #8's server-side scope.

## OAuth and webhook helper targets

These are separate non-catalog contracts, not extra catalog operations. P04 implements the OAuth rows; see the [OAuth guide](../oauth.md). The webhook row remains planned for #13/P05 in this checkout.

| Target | Inputs/wire mapping | Result and ownership |
| --- | --- | --- |
| `OAuthService::authorizationUrl(AuthorizationRequest)` | `client_id`, configured exact `redirect_uri`, `response_type=code` in query at the app authorize URL. Encode the complete redirect URI, including any consumer correlation query. | Authorization URL value. Consumer owns callback, correlation and denial handling. Do not assume undocumented `state` support or host a route. |
| `OAuthService::exchangeCode(CodeExchangeRequest)` | POST token URL; documented query keys `client_id`, `client_secret`, `grant_type=authorization_code`, `code`, `redirect_uri`. | `TokenResult`: `access_token:string`, `token_type:string`, `expires_in:int`, `refresh_token:string`, `scope:list<string>` from the technical reference. Never log the credential-bearing URL. |
| `OAuthService::refresh(RefreshTokenRequest)` | POST token URL; documented query keys `client_id`, `client_secret`, `grant_type=refresh_token`, `refresh_token`. | Same typed token result. Consumer persists returned tokens and owns renewal policy; no hidden storage/automatic refresh promise. |
| `WebhookVerifier::verify` / `WebhookParser::parse` | Original raw body bytes and `X-Wistia-Signature`; shared configured secret. HMAC **SHA-256 hex** over raw bytes, constant-time comparison, verification before JSON parsing. | Planned verified typed envelope with `hook.uuid` and batched `events` (`uuid`, `type`, `generated_at`, `payload`), preserving unknown event payloads. Consumer owns HTTP routing, deduplication, ordering and processing. |

Sources: [OAuth technical reference](https://docs.wistia.com/docs/authenticating-with-oauth2.md) and [webhook headers/body](https://docs.wistia.com/docs/webhooks.md). The OAuth guide limits authorization to account owners/managers and says OAuth is not yet available to all accounts; Wistia enablement may be required ("Get Approved"). The [OAuth guide](../oauth.md) carries both prerequisites; this does not authorize contacting Wistia or provisioning an account. The webhook guide describes duplicate/out-of-order and batched delivery; parsing a valid signature does not imply replay prevention. Tests/docs for these helpers are #12/#13 obligations, not inventory-checker coverage.

### Safe local inventory checks

No dependencies, credentials, network or legacy tests are needed:

```sh
php -l tools/check-inventory.php
php -d allow_url_fopen=0 tools/check-inventory.php --self-test
php -d allow_url_fopen=0 tools/check-inventory.php --require-complete
```

Default mode checks pinned catalog membership/counts, inclusion/exclusion safety, unique methods, path-input mapping, the narrative-derived caption format selector and wire-schema references. A presence-only digest pins the documented catalog response schema slots (operation/status/content type), rejecting omitted schema mappings without requiring schemas for genuinely schema-less responses or unresolved Upload workflows. This is a bounded inventory regression guard, not a full source-semantic audit; source changes require reviewing and refreshing the pin against retained documentation. The self-test mutates in-memory inventory copies to verify rejection of missing/duplicate/unsafe mappings and hidden gaps. These are **inventory-checker tests only**, not synthetic endpoint contract tests. `--require-complete` deliberately exits nonzero while named source-contract gaps remain. This full-contract completeness gate is not P01's approved inventory/planning completion gate: P01 may retain the four explicitly assigned P16 gaps, but P16 must resolve them before implementing or accepting those workflows. A default accounting pass does not mean downstream contract readiness. The checker does not prove PHP DTO implementations, remote source truth, every encoding detail or live account entitlement.

Planned endpoint tests use controlled HTTP requests/responses without network, on PHP 8.4 and a newer supported runtime. Test applicable auth, paths, version, encoding, result and error/redaction cases, plus pagination, finite polling, local validation and ambiguous-write/no-retry behavior. #10 must isolate default discovery from the destructive legacy suite. Never run the existing PHPUnit suite as this documentation check. Live tests remain separate opt-in, with additional destructive approval and no charge-incurring calls under #8.

P01 alone changed no runtime behavior or dependency declaration. P02 adds the [shared foundation](../foundation.md), Composer modernization and authored offline tests. P04 adds the [OAuth helpers](../oauth.md); catalog endpoint mappings remain planned in this checkout. No changelog entry or release-impact label is warranted for P01 alone; the eventual breaking rewrite's 2.0.0 target remains unchanged and does not authorize release.
